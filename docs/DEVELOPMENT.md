# 开发规范

适用于本项目的代码、配置和文档改动。

## 范围与实现

- 开始前检查工作区和相关现有实现，保留无关改动；先完成用户要求的最小可用范围，不顺手扩大功能。
- Node.js 项目使用 `pnpm`。新写 TypeScript 业务结构优先定义 `interface`；避免无必要的 `any`，先检查类型边界和数据结构。
- 代码按领域拆分，避免把业务文件长期平铺在 `utils/` 根目录。新文件超过 **600 行**时，除明确的特殊业务需求外必须拆分；特殊情况要说明原因。不要为了凑行数机械拆散紧密的逻辑。
- 不使用 Mock 数据，不新增测试用例，除非用户明确要求。任务结束前清理临时日志与 Debug 代码；无需额外启动 Dev 服务器，除非用户要求。
- 遇到版本、API 入参或配置问题，先核对项目实际依赖与官方文档；反复遇到同一错误时查对应的 GitHub Issues、Stack Overflow 等资料，不在同一种失败尝试上空转。

## 提交规范

- 仅在用户要求或已有授权时提交、推送。提交消息遵循 Conventional Commits：英文 `type` 与 `scope`，冒号后的说明用简体中文，例如 `feat(admin): 调整站点设置页面`。
- 提交前检查改动范围、行尾换行与 `git diff --check`，不要把无关文件带入提交；跨平台文本文件使用正常的行尾换行。

## 本地验证

- 每次任务完成前运行 `pnpm format` 和 `pnpm build`，并按改动范围执行必要的 lint、类型、i18n 解析或引用检查；只有用户明确免除时才跳过。文档或小范围 UI 改动也不能默认省略 Build。
- 全量 Build 最长等待约 300 秒；超时、失败或环境阻塞要明确说明，不能写成“已通过”。Build 通过只证明代码可构建，不代表部署环境或浏览器中的交互已验证。
- 不为验证而额外编写测试用例；用户要求测试时再按目标行为补充。
